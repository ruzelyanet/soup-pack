## 1. Модель данных (обзор)

```
request-form ──< request >── client
                   │  │
     request-column│  └── order ──< transaction
         │         │
   request-goal ──< request-goal-state
                   │
             request-event (история/аудит)
```

Общие правила:

- **Деньги — целые сумы (UZS), без копеек.** Новые денежные поля — `integer`. Существующие `decimal` в `order` не трогаем, но в коде всегда приводим через `Number()` и округляем.
- **Ничего не удаляем физически** из заявок, заказов и транзакций: архив, отмена или сторно.
- Все изменения статусов, назначений и денег пишутся в историю (кто, когда, что).
- Бизнес-логика — в сервисах/кастомных контроллерах Strapi, не во фронтенде. Фронт не присылает суммы, которым мы доверяем.
- ⚠️ **Не хранить цели колонок как repeatable component.** В Strapi 5 при обновлении компонента его записи пересоздаются с новыми id, и ссылки из состояний заявок сломаются. Цели — отдельная коллекция.

## 2. Заявки

### 2.1. Типы заявок

Два фиксированных типа (enum, не справочник):

| Значение | Подпись |
|---|---|
| `individual` | Физ. лицо |
| `shop` | Магазин |

**Тип определяется формой, а не телом запроса.** Для магазинов и физлиц создаются разные формы (разные ссылки/ключи), и тип берётся из настроек формы. Если внешний источник прислал `type` в body — игнорируем его, иначе любой может прислать заявку «не того» типа. При ручном создании сотрудник выбирает тип сам.

На доске одна общая доска с фильтром по типу и цветным бейджем типа на карточке (колонки общие для обоих типов). Тип можно сменить вручную, пока заявка не превращена в заказ.

### 2.2. Content-type `request`

| Поле | Тип | Примечание |
|---|---|---|

| `type` | enum `individual\|shop` | обязательно |
| `name` | string, required | |
| `phone` | string, required | нормализуем в `+998XXXXXXXXX` (общая утилита с `client`) |
| `values` | json | ответы на поля формы: `[{ key, label, value }]` — label сохраняется снимком, чтобы заявка читалась после редактирования формы (как `request_fields` в eventra) |
| `extra` | json | всё, что пришло сверх известных полей, + `utm_*`, `referrer` |
| `comment` | text | внутренний комментарий сотрудника |
| `source` | enum `manual\|form\|api` | |

| `form` | relation manyToOne → `request-form` | null при ручном создании |

| `lockedAt` | datetime | ставится при создании заказа |
| `archived` | boolean | default false |
| `createdBy` | relation → `employee` | для ручных |

### 2.3. Колонки (статусы) — как в eventra

Content-type `request-column`: `name`, `color`, `kind` (`new|custom|done`), `position`.

- **Две колонки зашиты:** `new` («Новые заявки», всегда первая) и `done` («Готово», всегда последняя; в eventra `position = 1_000_000`). Создаются автоматически в bootstrap, если их нет (аналог `ensureDefaultColumns`). Их нельзя удалить; переименовать и сменить цвет можно.
- Колонки `custom` создаются/переименовываются/удаляются админом и встают между `new` и `done`. Порядок меняется перетаскиванием.
- Удалить `custom`-колонку можно только пустую (`COLUMN_NOT_EMPTY`), как в eventra.
- В колонке `new` — кнопка «+ Заявка» (ручное создание).
- В колонке `done` у каждой карточки — кнопка **«Создать заказ»**; если заказ уже создан — ссылка «Заказ SP-…».

### 2.4. Цели колонки

Коллекция `request-goal`: `column` (manyToOne), `text`, `position`.
Коллекция `request-goal-state`: `request`, `goal`, `column`, `done` (bool), `removed` (bool), уникальность `(request, goal)`.

Поведение (повторяет eventra, где это две таблицы `request_goal_snapshots` + `request_goal_completions` — здесь объединены в одну):

1. Админ управляет списком целей колонки в диалоге «Управление целями» (добавить, переименовать, удалить).
2. Когда заявка попадает в колонку, для неё создаются `goal-state` по всем текущим целям колонки. Пока заявка стоит в колонке, новые цели колонки досоздаются (`INSERT OR IGNORE`-семантика); уже снятые вручную не возвращаются.
3. После ухода из колонки её чек-лист замораживается и показывается в истории заявки как итог: ✓ выполнено / ✗ не выполнено.
4. На карточке — прогресс `выполнено/всего` и чек-лист; у заявки можно убрать отдельную цель и «Восстановить все цели».
5. Цели **не блокируют** перемещение (как в eventra). Опционально, флаг колонки `requireGoals` — запрещать уход из колонки, пока не выполнены все цели. По умолчанию выключен.

### 2.5. Принятие заявки

- Новая заявка без ответственного видна в колонке `new` всем сотрудникам с ролью `manager` и `duty` (очередь). Курьерам доска заявок не показывается.
- На карточке и на странице заявки — кнопка **«Принять»**. Принять заявку может только один человек.
- После принятия: `assignee` = сотрудник, `acceptedAt` = now, заявка **автоматически переходит в первую custom-колонку** (если custom-колонок нет — остаётся в `new`, но уже с ответственным). Событие `accepted` в истории.
- После принятия заявка **пропадает из очереди у остальных** сотрудников (`duty`). Видимость: `duty` видит очередь неназначенных + свои; `manager` видит всё.
- `manager` может переназначить заявку на другого сотрудника (событие `reassigned`) и снять назначение (вернуть в очередь).
- Двигать заявку по колонкам, редактировать и конвертировать может только её ответственный или `manager`. Заявку без ответственного нельзя вывести из `new` ничем, кроме «Принять».

**Атомарность обязательна.** Два сотрудника могут нажать «Принять» одновременно. Реализация — условный UPDATE в транзакции через knex, а не «прочитать → проверить → записать»:

```ts
// backend/src/api/request/services/request.ts (набросок)
await strapi.db.transaction(async ({ trx }) => {
  const affected = await strapi.db.connection('requests')
    .transacting(trx)
    .where({ id: requestId })
    .whereNull('accepted_by_id')
    .update({ accepted_by_id: employeeId, accepted_at: new Date() })
  if (affected === 0) throw new ApplicationError('ALREADY_TAKEN') // → HTTP 409
  // затем: установить relation assignee, переместить в первую custom-колонку,
  // создать goal-state, записать request-event
})
```

Имя таблицы/колонок проверь по фактической схеме Strapi (`.tmp/data.db`). Фронт при 409 показывает «Заявку уже принял {имя}» и перезагружает доску.

Доска обновляется опросом каждые 15–20 секунд (и сразу после любого своего действия). WebSocket/SSE — не сейчас.

### 2.6. Клиент и дубликаты

- При создании заявки ищем `client` по нормализованному телефону. Если есть — привязываем. Если нет — **клиента не создаём** до конвертации в заказ (заявка — ещё не клиент); создаём при «Создать заказ».
- Если у этого телефона уже есть открытая заявка (`outcome = open`, не в архиве), новую всё равно создаём, но помечаем `extra.duplicateOf = <code>` и показываем на карточке предупреждение «Есть открытая заявка RQ-…» со ссылкой. Склеивание — вручную (не в этой итерации).

### 2.7. Завершение без заказа

Чтобы заявки не «висели» вечно, кроме конвертации есть действие **«Закрыть без заказа»** (обязательная причина из списка: «не дозвонились», «дорого», «не наш район», «передумал», «дубль», «другое» + текст). Заявка получает `outcome = lost`, уходит с доски в раздел «Все заявки» (фильтр «Закрытые»). Можно переоткрыть (`manager`) — вернётся в `new` без ответственного.

Это не третья фиксированная колонка, а действие из меню заявки — так две зашитые колонки остаются двумя.

### 2.8. Страница заявки

Отдельный маршрут `admin: /requests/:id` (по образцу `details/index.vue` в eventra):

- Шапка: код, тип, источник, ответственный (кнопка «Принять» / «Переназначить» для manager), текущая колонка, действия: «Редактировать», «Закрыть без заказа», «В архив».
- Контакты: имя, телефон (кликабельный `tel:`), ссылка на клиента, если найден.
- Ответы формы (`values`) и доп. данные (`extra`), редактируемые до блокировки.
- Комментарий сотрудника.
- История: колонки с датой входа, у текущей — живой чек-лист, у прошлых — итог целей; плюс события принятия/переназначения/правок.
- Блок «Заказ»: кнопка «Создать заказ» (доступна в колонке `done`) или карточка созданного заказа со ссылкой.
- После создания заказа заявка **заблокирована** (`lockedAt`): правки полей запрещены (сервер возвращает `REQUEST_LOCKED`), остаются только просмотр и история — как в eventra.

Плюс страница «Все заявки» — таблица с поиском по имени/телефону/коду и фильтрами: тип, колонка, ответственный, исход, источник, период.

### 2.9. SLA (минимум)

- Таймер на карточке в `new`: сколько ждёт принятия. Жёлтый > 10 мин, красный > 30 мин (пороги в настройках, single type `request-settings`).
- На дашборде: неназначенные заявки, среднее время до принятия, конверсия заявка → заказ по сотрудникам и по типам.
- Уведомление в Telegram о новой заявке и о просроченной — фаза 5 (точка подключения: lifecycle `afterCreate` у `api::request.request`).

## 3. Формы заявок

### 3.1. Content-type `request-form`

| Поле | Тип | Примечание |
|---|---|---|
| `name` | string | внутреннее название («Сайт — магазины») |
| `slug` | uid | часть публичной ссылки |
| `type` | enum `individual\|shop` | определяет тип создаваемых заявок |
| `isActive` | boolean | неактивная форма отвечает 404/410 |
| `title`, `description` | string/text | заголовок и текст публичной формы |
| `fields` | json | схема доп. полей (см. ниже) |
| `successMessage` | text | что показать после отправки |
| `apiKey` | string, private | ключ для внешних интеграций; хранить хеш, показывать один раз при генерации |
| `requireApiKey` | boolean | true — форма принимает только серверные запросы с ключом (нет публичной страницы) |
| `sourceDetail` | string | по умолчанию проставляется в заявку (`instagram`, `site`…) |

`name` и `phone` **всегда обязательны и не настраиваются** — они не входят в `fields`, форма всегда их содержит.

Схема элемента `fields`:

```json
{
  "key": "district",
  "label": "Район",
  "type": "text | textarea | number | select | date | checkbox | address",
  "required": false,
  "options": ["Юнусабад", "Чиланзар"],
  "placeholder": "",
  "position": 1
}
```

`key` — латиница, уникален в форме, не меняется после создания (по нему матчим данные внешних систем). Удалённое поле перестаёт показываться, но уже сохранённые в заявках значения остаются (у них снимок label).

Редактор формы в админке: список полей с перетаскиванием, тип, обязательность, варианты для `select`; превью формы; блок «Подключение» с публичной ссылкой, примером `curl` и кнопкой «Сгенерировать новый ключ».

### 3.2. Способы приёма заявок

**A. Готовая ссылка.** В клиентском приложении маршрут `/f/:slug` рендерит форму по схеме из `GET /api/request-forms/public/:slug`. После отправки — `successMessage`. Ссылку можно ставить в шапку Instagram, на сайт, в QR на упаковке.

**B. Сторонние формы (сайт, Instagram через сервисы-интеграторы, Tilda, Google Forms и т.п.).** Внешняя система сама собирает данные и отправляет POST:

```
POST /api/request-forms/:slug/submit
X-Form-Key: <apiKey>              // обязателен, если requireApiKey; иначе опционален
Idempotency-Key: <uuid>           // опционально, защищает от повторной отправки
Content-Type: application/json

{
  "name": "Алишер",
  "phone": "90 123 45 67",
  "fields": { "district": "Чиланзар", "comment": "Нужно 20 шайб в неделю" },
  "meta": { "utm_source": "instagram", "referrer": "..." }
}
```

Ответ `201 { data: { code: "RQ-000123" } }`.

Правила приёма:

- `name` и `phone` обязательны → иначе `400` с перечнем ошибок по полям. Телефон нормализуем; некорректный → `400`.
- Обязательные поля из `fields` формы проверяются; неизвестные ключи не отбрасываются, а кладутся в `extra`.
- Тип — из формы, `type` в body игнорируется.
- Тот же `Idempotency-Key` в течение 24 ч возвращает уже созданную заявку, а не новую.
- Защита публичной формы: honeypot-поле, rate limit по IP (например, 10 заявок/10 мин), ограничение размера body. Ключ формы никогда не попадает во фронтенд клиентского приложения.
- Ручное создание из админки и все внешние источники проходят через **один сервис** `createRequest()` — одинаковая валидация, нормализация, привязка клиента, история.

## 4. Заказы

Существующий `order` дорабатываем:

| Новое поле | Тип | Примечание |
|---|---|---|
| `source` | enum `catalog\|request\|manual` | `place` → `catalog` |
| `request` | relation oneToOne → `request` | если создан из заявки |
| `createdBy` | relation → `employee` | для `request`/`manual` |
| `paidAmount` | integer | сумма подтверждённых платежей минус возвраты (кешируется сервисом) |
| `paymentStatus` | enum `unpaid\|partial\|paid\|overpaid\|refunded` | пересчитывается сервисом, не редактируется руками |
| `transactions` | relation oneToMany → `transaction` | |

### 4.1. Единый расчёт заказа

Вынести из `controllers/order.ts → place()` логику нормализации строк, пересчёта `subtotal`, скидки на чек (`pickTier`) и генерации `code` в сервис `order.buildAndCreate(input, { source, createdBy })`. Его используют:

- `POST /api/orders/place` (каталог) — поведение не меняется;
- ручное создание в админке;
- «Создать заказ» из заявки.

Сервер всегда пересчитывает суммы по ценам продуктов из БД, цены из запроса для известных `productId` не берутся на веру (сейчас `place()` берёт `price` из body — это нужно исправить тем же изменением).

### 4.2. Ручное создание заказа

Кнопка «+ Заказ» на странице заказов. Форма: клиент (поиск по телефону/имени или новый), позиции (продукты и наборы из каталога, количество), способ доставки и слот, адрес, способ оплаты, комментарий. Предпросмотр итога приходит с сервера (`POST /api/staff/orders/preview` — тот же расчёт без сохранения).

### 4.3. «Создать заказ» из заявки

Открывает ту же форму, предзаполненную из заявки: имя, телефон, адрес/район из `values`, комментарий. Сотрудник добавляет позиции. При сохранении в одной транзакции:

1. upsert `client` по телефону (как в `place()`), тип клиента — из типа заявки;
2. создание заказа с `source = request`, `request`, `createdBy`;
3. заявка: `order`, `outcome = converted`, `lockedAt`, событие `converted`.

Повторное создание для той же заявки → `409 REQUEST_ALREADY_CONVERTED`. Одна заявка → один заказ. Повторные заказы того же клиента создаются вручную или из карточки клиента.

### 4.4. Оплата в карточке заказа

В диалоге/странице заказа:

- видно **способ оплаты** (выбранный клиентом/сотрудником), сумму заказа, оплачено, остаток и `paymentStatus` бейджем;
- кнопка **«Принять оплату»** → создаёт транзакцию (раздел 5);
- список транзакций заказа с возможностью сторно (для `manager`);
- в таблице заказов — колонка статуса оплаты и фильтр «Не оплачены».

Статус выполнения (`status`) и статус оплаты (`paymentStatus`) независимы: заказ может быть доставлен и не оплачен, и наоборот.

При отмене заказа, у которого `paidAmount > 0`, сервер не запрещает отмену, но в ответе и в UI появляется требование «Оформите возврат N сум»; заказ подсвечивается в фильтре «Нужен возврат».

## 5. Транзакции

Транзакция — неизменяемая запись о движении денег по заказу. Деньги никогда не правятся задним числом: ошибку исправляют сторно и новой транзакцией.

### 5.1. Content-type `transaction`

| Поле | Тип | Примечание |
|---|---|---|
| `code` | string, unique | `TX-000123` |
| `kind` | enum `payment\|refund` | приход от клиента / возврат клиенту |
| `order` | relation manyToOne → `order`, required | |
| `client` | relation manyToOne → `client` | копируется из заказа, для отчётов |
| `method` | enum `cash\|card\|click\|payme\|transfer` | тот же набор, что `order.paymentMethod`; по умолчанию берётся из заказа, можно изменить |
| `amount` | integer, > 0 | всегда положительная; знак определяется `kind` |
| `currency` | string | `UZS`, на будущее |
| `status` | enum `completed\|cancelled` | |
| `paidAt` | datetime | фактическое время оплаты (можно указать задним числом в пределах 7 дней) |
| `receivedBy` | relation → `employee` | кто фактически получил деньги (важно для наличных у курьера) |
| `createdBy` | relation → `employee` | кто внёс запись |
| `comment` | text | |
| `externalId` | string, unique, nullable | id платежа в Payme/Click/банке — защита от двойного учёта при будущей интеграции |
| `idempotencyKey` | string, unique | генерирует фронт при открытии диалога; повторная отправка не создаёт дубль |
| `cancelledAt`, `cancelledBy`, `cancelReason` | | заполняются при сторно |

### 5.2. Правила

- **Создание платежа** (`POST /api/staff/orders/:id/payments`): `amount > 0`, по умолчанию = остаток. Сумма больше остатка — запрещена (`AMOUNT_EXCEEDS_BALANCE`), кроме случая, когда `manager` явно ставит флаг «переплата» (тогда `paymentStatus = overpaid`). На отменённый заказ платёж нельзя.
- **Возврат** (`POST /api/staff/orders/:id/refunds`): только `manager`; сумма ≤ `paidAmount`; причина обязательна.
- **Сторно** (`POST /api/staff/transactions/:id/cancel`): только `manager`, причина обязательна; `status = cancelled`. Отменённая транзакция не участвует в суммах, но видна в истории. Редактирования и удаления нет вообще.
- **Пересчёт заказа** — в той же DB-транзакции, что и изменение транзакции:
  `paidAmount = Σ payment(completed) − Σ refund(completed)`;
  `paymentStatus`: `0` → `unpaid` (или `refunded`, если были возвраты), `< total` → `partial`, `= total` → `paid`, `> total` → `overpaid`.
- Каждое действие пишет событие в историю заказа (если истории заказа нет — завести коллекцию `order-event` по образцу `request-event`).
- Курьер может принять оплату только по заказу, где он назначен (`order.employee`), и только с `receivedBy = он сам`.

### 5.3. Раздел «Транзакции» в админке

- Таблица: дата, код, заказ, клиент, тип, способ, сумма, получил, статус. Фильтры: период, способ, сотрудник, тип, статус.
- Итоги по выбранному периоду в разрезе способов оплаты: приход, возвраты, нетто.
- **Наличные на руках**: по каждому сотруднику сумма наличных платежей, где он `receivedBy`. (Сдача наличных в кассу — сущность `cash-handover` — следующая итерация, но поле `receivedBy` нужно уже сейчас, чтобы данные были.)
- Выручку на дашборде (`Dashboard.vue`) показывать двумя метриками: «Продажи» (по заказам) и «Поступления» (по транзакциям).

Онлайн-интеграция Payme/Click в эту итерацию не входит: платежи вносятся вручную, `externalId` зарезервирован.

## 6. Пользователи, роли и безопасность — обязательная база

Сейчас в коде два риска, которые блокируют модули выше:

1. **Публичные права на чтение заказов и клиентов.** В `backend/src/index.ts → PUBLIC_ACTIONS` для public-роли открыты `api::order.order.find` и `api::client.client.find`: любой может получить список всех заказов и клиентов с телефонами и адресами. Убрать эти права; если клиентскому приложению нужна история заказов — сделать отдельный эндпоинт, отдающий заказы только своего телефона после входа.
2. **Админка работает через full-access API-токен из `admin/.env`.** Токен попадает в собранный JS и даёт полный доступ любому, кто откроет админку. Кроме того, при общем токене сервер не знает, какой сотрудник нажал «Принять» — а на этом построено закрепление заявок.

Решение (минимальное):

- `POST /api/staff/sign-in { phone, personalKey }` → JWT с `employeeId` и `role` (можно выпускать через `strapi.plugin('users-permissions').service('jwt').issue(...)`). `personalKey` в БД хранить хешем.
- Глобальная policy `global::is-staff` проверяет токен, кладёт сотрудника в `ctx.state.employee`, опционально проверяет роль: `is-staff({ roles: ['manager'] })`.
- Все новые эндпоинты админки — под префиксом `/api/staff/*` с этой policy. Существующие CRUD админки постепенно переводятся туда же; `VITE_API_TOKEN` из админки убирается.
- `LoginPage.vue` админки — вход по телефону и ключу, токен в Pinia + `localStorage`, axios-интерцептор подставляет `Authorization`, на 401 — выход на логин.

Права:

| Действие | manager | duty | courier |
|---|---|---|---|
| Видеть очередь новых заявок, принимать | ✓ | ✓ | — |
| Видеть все заявки | ✓ | только свои | — |
| Двигать/редактировать/конвертировать заявку | ✓ | свои | — |
| Переназначать, переоткрывать | ✓ | — | — |
| Настраивать колонки, цели, формы | ✓ | — | — |
| Создавать заказ вручную | ✓ | ✓ | — |
| Принимать оплату | ✓ | ✓ | по своим заказам |
| Возврат, сторно | ✓ | — | — |
