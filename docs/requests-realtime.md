# SoupPack — Заявки в реальном времени

Техническое задание для Claude Code. Новые и изменённые заявки появляются в админке сами, без обновления страницы. Новая заявка показывает уведомление с кнопкой «Открыть» и сразу появляется на доске и в таблице. Механизм — **Server-Sent Events (SSE)**, выбран как самый экономный для сервера.

> Перед началом прочитай этот файл целиком, затем `docs/requests-orders-transactions.md` (модель заявок) и текущий код из раздела 1. Если код расходится с описанием — ориентируйся на код и отметь расхождение в итоговом отчёте.
>
> Сначала покажи план и список файлов к изменению — и жди подтверждения.

---

## 0. Ключевые принципы

1. **Сервер ничего не делает, пока ничего не происходит.** Никаких опросов по таймеру, пока SSE работает. Пинг раз в 25 с — несколько байт, без запросов в БД.
2. **Одно соединение на браузер, а не на вкладку.** Вкладки договариваются между собой (Web Locks + BroadcastChannel), соединение держит одна.
3. **Событие — это сигнал, а не данные.** В событии только короткая информация для уведомления. Строку для таблицы админка догружает обычным API — с теми же правами и фильтрами, что и сейчас.
4. **Сервер — единственный источник правды о видимости.** Попадает ли заявка в текущий фильтр, решает сервер (тот же `list`), админка не дублирует логику ролей и scope.
5. **Ничего не теряется.** При каждом (пере)подключении — одна сверка списка. Пропущенное за время обрыва подтянется.
6. **Существующую логику заявок не меняем.** Принятие, перемещение, цели, SLA, Telegram — как есть.

## 2. Бэкенд

### 2.1. Шина событий — `backend/src/utils/realtime.ts` (новый)

```ts
export type RealtimeEvent =
  | { type: 'request.created'; requestId: number; summary: RequestSummary; actorId: number | null }
  | { type: 'request.updated'; requestId: number; kind: string; actorId: number | null }
  | { type: 'request.reordered'; columnId: number; actorId: number | null }
  | { type: 'request.overdue'; requestId: number; summary: RequestSummary }

export type RequestSummary = {
  id: number; code: string; type: 'individual' | 'shop'; name: string;
  source: 'manual' | 'form' | 'api'; sourceDetail: string | null; createdAt: string;
}
```

- Интерфейс `RealtimeBus { publish(e), subscribe(fn): unsubscribe }`, реализация по умолчанию — `EventEmitter` в памяти процесса. Интерфейс нужен, чтобы позже заменить на PostgreSQL `LISTEN/NOTIFY` при запуске нескольких процессов (сейчас **не делать**, только оставить место).
- Каждому событию присваивается возрастающий `seq` (номер с момента старта процесса) и `at` (ISO-время).
- **Телефон в событиях не передаём** — уведомлению он не нужен.

### 2.2. Откуда отправлять события

| Событие | Где | Примечание |
|---|---|---|
| `request.created` | `logEvent` при `kind === 'created'` | загрузить короткую строку (`select` полей `RequestSummary`), одна выборка на событие |
| `request.updated` | `logEvent` при любом другом `kind` (`accepted`, `moved`, `patched`, `reassigned`, `lost`, `reopened`, `converted`, цели…) | `kind` = вид события |
| `request.reordered` | контроллер `reorder` после цикла обновлений | `logEvent` там не вызывается — добавить публикацию явно |
| `request.overdue` | `scanOverdueRequests` после пометки `overdueNotifiedAt` | независимо от того, включён ли Telegram: вынести отправку в шину из-под проверки `telegramEnabled` / токена — проверь, чтобы сама проверка просрочки не зависела от Telegram, и отметь в отчёте, как сделал |

- Публиковать **после** записи в БД. Сейчас `logEvent` вызывается вне транзакций — проверь все места вызова. Если где-то он окажется внутри `strapi.db.transaction`, публикацию отложить до коммита.
- Ошибка публикации не должна ломать основной запрос: `try/catch` + `strapi.log.warn`.

### 2.3. Маршрут `GET /staff/events`

- Файл маршрута — новый API `backend/src/api/realtime/` (routes + controller) или `routes` в существующем `request`; выбери, что чище, и объясни в отчёте.
- Политика `global::is-staff` с `roles: ['manager', 'duty']` (как у раздела «Заявки»), `auth: false`.
- Ответ:
  - заголовки: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `Connection: keep-alive`, `X-Accel-Buffering: no`;
  - `ctx.req.socket.setTimeout(0)`, `setNoDelay(true)`, `setKeepAlive(true)`;
  - `ctx.status = 200`, `ctx.body = new PassThrough()`;
  - первым сообщением — `retry: 5000` и событие `hello` с `{ seq, serverTime }`.
- Формат каждого события:
  ```
  id: <seq>
  event: <type>
  data: <JSON>

  ```
- Пинг: комментарий `: ping` каждые 25 с.
- При закрытии соединения (`close` у `ctx.req`) — отписаться от шины и остановить таймер пинга. Утечек подписчиков быть не должно.
- Лимит: не больше 5 одновременных соединений на сотрудника; при шестом закрыть самое старое. Счётчик — `Map<employeeId, Set<stream>>`.
- Токен истёк или сотрудник удалён → политика вернёт 401 до открытия потока; клиент на 401 делает logout (3.1).
- При остановке Strapi — закрыть все потоки (`strapi.server.httpServer.on('close')`, как сделано для `overdueTimer`).
- Логи: подключение/отключение — `debug`, превышение лимита — `info`.

### 2.4. Фильтр списка по id — `GET /staff/requests?ids=1,2,3`

Добавить в `list` необязательный параметр `ids` (через запятую, до 50). Он **сужает** выборку, все остальные фильтры и правила scope/роли работают как сейчас.

Зачем: админка получила событие о заявке 1042 → спрашивает `list` с текущими фильтрами страницы + `ids=1042`. Пришла строка — заявка видна и подходит под фильтр; пустой ответ — не подходит или нет прав. Так логика видимости остаётся только на сервере.

### 2.5. Тесты (`backend/tests/`, vitest)

- шина: `publish` доходит до подписчика, `unsubscribe` работает, `seq` растёт;
- `logEvent('created')` публикует `request.created` с `summary` без телефона; другой `kind` → `request.updated`;
- `reorder` публикует `request.reordered`;
- `list` с `ids` + scope `mine` у duty не отдаёт чужую заявку;
- маршрут: без токена — 401, роль `courier` — 403. Если поднять поток в тесте сложно — вынести форматирование SSE-сообщения в чистую функцию и протестировать её.

## 3. Админка: подключение и данные

### 3.1. Клиент SSE — `admin/src/services/realtime.ts` (новый)

- Чтение потока через `fetch` (библиотека `@microsoft/fetch-event-source`): стандартный `EventSource` не умеет передавать заголовок `Authorization`. Базовый URL — тот же `API_URL`, токен — из `useAuth()`.
- `openWhenHidden: true` — не рвать соединение при сворачивании вкладки (дешевле, чем переподключаться).
- Переподключение: пауза 1 → 2 → 4 → 8 → 16 → 30 с (дальше 30) + случайные ±20%. Сброс паузы после успешного `hello`.
- Ответ 401 → прекратить попытки, `auth.logout()` и редирект на логин (как в `api.ts`). 403 → прекратить попытки молча.
- Отслеживать `seq`: событие с `seq`, который уже видели, игнорировать. Если после переподключения `hello.seq` меньше последнего известного — сервер перезапускался → сделать сверку (3.3).
- Состояние соединения: `connecting | open | fallback | off`.

### 3.2. Одно соединение на браузер — Web Locks + BroadcastChannel

- Вкладка пытается взять блокировку `navigator.locks.request('souppack-realtime', …)`. Взявшая — **ведущая**: держит SSE-соединение и пересылает каждое событие в `BroadcastChannel('souppack-realtime')`. Остальные только слушают канал.
- Закрылась ведущая вкладка → блокировку берёт следующая и открывает соединение сама.
- При logout — освободить блокировку и закрыть соединение во всех вкладках (сообщение `logout` в канал).
- Нет поддержки Web Locks (старый браузер) → каждая вкладка держит своё соединение, это допустимо.
- **Звук и системное уведомление проигрывает только ведущая вкладка**, toast показывают все видимые вкладки.

### 3.3. Pinia-стор — `admin/src/stores/requestsFeed.ts` (новый)

Единая точка, через которую страницы получают события.

```ts
state: {
  status: 'connecting' | 'open' | 'fallback' | 'off'
  unseenIds: number[]          // новые заявки, которые сотрудник ещё не открыл
  lastSyncAt: string | null
}
// подписки страниц:
onCreated(fn), onUpdated(fn), onReordered(fn), onResync(fn)  // возвращают unsubscribe
markSeen(id)
```

- Запускается из `AdminLayout.vue` при входе (роли `manager`, `duty`), останавливается при logout. Курьеру не подключать.
- `onResync` вызывается при каждом успешном (пере)подключении и при выходе из режима `fallback` — страницы в ответ перезапрашивают свои данные **один раз**.
- **Запасной режим:** если SSE не открылось 3 попытки подряд → `fallback`: раз в 60 с вызывать `onResync`, пока вкладка видна (`document.visibilityState === 'visible'`). При успешном подключении — выйти из `fallback`.
- `unseenIds` хранить в `sessionStorage` (переживает перезагрузку страницы, не переживает закрытие браузера). Убирать id, когда заявку открыли (`RequestDetails`), когда её приняли (`request.updated` с `kind = accepted`) или закрыли.
- Не добавлять в `unseenIds` и не показывать уведомление, если `actorId === auth.employee.id` (сотрудник сам создал заявку).

## 5. Заявка появляется в списках

Общее правило для каждой страницы: получили событие → запросили `Requests.list({ ...текущие фильтры страницы, ids: [id] })` → если строка пришла — вставить или заменить её по `id`; если пустой ответ — убрать строку с этим `id`, если она была. Несколько событий подряд (до 300 мс) объединять в один запрос с несколькими `ids`.

### 5.1. Доска — `Board.vue`

- **Удалить** `setInterval(fetchAll, 20000)` и `pollTimer`.
- Подписаться на `onCreated`, `onUpdated`, `onReordered`, `onResync`; отписаться в `onUnmounted`.
- `request.created` / `request.updated` → правило выше (с фильтрами `type`, `scope`, `outcome: 'open'`). Заявка, перешедшая в другую колонку, переезжает в ней.
- `request.reordered` → перезапросить только заявки этой колонки (`list` с `columnId`) и обновить их `position`.
- `onResync` → `fetchAll()`.
- **Порядок в колонках не менять** (старые сверху — важно для SLA). Новая карточка:
  - подсвечивается: мягкий tomato-фон, который плавно гаснет за 3–4 с;
  - получает метку «Новая» (маленький чип рядом с кодом в `RequestCard.vue`), пока `id` есть в `unseenIds`;
  - если колонка прокручена и карточка вне видимости — в шапке колонки плашка «+1 новая ↓», по клику — прокрутка к карточке.
- Своё действие сотрудника (принял, перетащил) не должно дёргаться дважды: оптимистичное обновление как сейчас, а пришедшее событие просто заменит строку той же версией.
- Если сотрудник прямо сейчас перетаскивает карточку — применять входящие обновления после окончания перетаскивания (очередь).

### 5.2. Таблица «Все заявки» — `AllRequests.vue`

- Сортировка по умолчанию — **`Создана` по убыванию** (новые сверху); остальные колонки сортируются кликом.
- Подписаться на те же события; фильтры для догрузки — текущие `type`, `outcome`, `columnId`, `q`, `scope: 'all'`.
- Новая строка вставляется сверху с той же подсветкой и меткой «Новая» в колонке «Код».
- **Не прыгать:** если таблица прокручена вниз больше чем на 200 px — строки добавляются, но над таблицей появляется плавающая плашка «↑ N новых заявок», по клику — прокрутка наверх и плашка исчезает.
- **Не подходит под фильтр:** если пришёл `request.created`, а догрузка с текущими фильтрами вернула пусто — не вставлять, а показать над таблицей плашку «N новых заявок не попадают в фильтр · Сбросить фильтры».
- `onResync` → `fetchAll()` с сохранением прокрутки.

### 5.3. Карточка заявки — `RequestDetails.vue`

- При открытии — `markSeen(id)`.
- `request.updated` по этой заявке от **другого** сотрудника → перезагрузить данные карточки и показать ненавязчивую плашку сверху: «Заявку изменил {имя}: {что — по `kind`}». Если сотрудник в этот момент редактирует поле — не перезаписывать ввод, а показать в плашке кнопку «Обновить».
- Особый случай: заявку принял другой сотрудник, пока этот её смотрел → плашка «Заявку принял {имя}», кнопки действий обновляются по правам.

## 6. Развёртывание

В итоговом отчёте — готовый фрагмент nginx для маршрута событий:

```nginx
location /api/staff/events {
    proxy_pass http://strapi_upstream;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 1h;
    chunked_transfer_encoding on;
}
```

- Включить HTTP/2 на сервере (`listen 443 ssl http2;`): при HTTP/1.1 браузер держит не больше 6 соединений на сайт, и много вкладок с открытыми потоками могли бы забить этот лимит. Решение из 3.2 (одно соединение на браузер) закрывает это и без HTTP/2, но HTTP/2 — дополнительная страховка.
- Если позже включат compression middleware — исключить `text/event-stream`.
- Strapi запущен **одним процессом** — шина в памяти работает. При запуске нескольких процессов нужна межпроцессная шина (2.1) — отдельная задача.

## 7. Не делать

- Не менять бизнес-логику заявок (принятие, перемещение, цели, SLA, Telegram).
- Не использовать WebSocket / socket.io.
- Не передавать в событиях телефон и полные данные заявки.
- Не делать межпроцессную шину (Redis, LISTEN/NOTIFY) — только интерфейс.
- Не добавлять реальное время в другие разделы (заказы, транзакции) — но шину и стор делать так, чтобы позже их можно было подключить.

## 9. Готово, когда

- [ ] Заявка с публичной формы появляется у менеджера на доске и в таблице за 1–2 с без обновления страницы.
- [ ] Появляется карточка-уведомление; «Открыть» ведёт в заявку; при наведении не исчезает; 4+ заявок подряд сворачиваются в «+ ещё N».
- [ ] Сотрудник, сам создавший заявку вручную, уведомления не получает.
- [ ] Бейдж на «Заявках» и число в заголовке вкладки растут и сбрасываются при открытии/принятии.
- [ ] Менеджер принял заявку — у дежурного она пропала из очереди сама; в открытой карточке у другого сотрудника — плашка «Заявку принял …».
- [ ] Перетаскивание карточки у одного сотрудника видно у другого.
- [ ] В таблице с фильтром «Магазины» новая заявка физлица не появляется, но видна плашка «не попадает в фильтр».
- [ ] Прокрученная таблица не прыгает — появляется плашка «↑ N новых».
- [ ] 5 открытых вкладок админки → на сервере **одно** SSE-соединение от этого браузера; закрыли ведущую — соединение подхватила другая.
- [ ] Остановили и запустили Strapi → админка сама переподключилась и подтянула заявки, созданные за это время.
- [ ] Пока событий нет, в логах/сети нет периодических запросов к `/staff/requests` (кроме режима `fallback`).
- [ ] Истёкший токен → выход на страницу логина, без бесконечных переподключений.
- [ ] Курьер к `/staff/events` не подключается (403).
- [ ] Тесты проходят.
