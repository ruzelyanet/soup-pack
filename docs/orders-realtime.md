# SoupPack — Заказы в реальном времени

Техническое задание для Claude Code. Новые и изменённые заказы появляются в админке сами, без обновления страницы. Новый заказ показывает уведомление с кнопками «Открыть» и «Взять в работу» и сразу появляется в таблице заказов.

Механизм — тот же, что в `docs/requests-realtime.md`: **Server-Sent Events (SSE)**, одно соединение на браузер, события — сигналы, данные догружаются обычным API.

> Перед началом прочитай этот файл целиком, затем `docs/requests-realtime.md` (общая инфраструктура реального времени), `docs/requests-orders-transactions.md` (модель заказов и транзакций) и текущий код из раздела 1. Если код расходится с описанием — ориентируйся на код и отметь расхождение в итоговом отчёте.
>
> Сначала проверь, сделана ли уже задача из `docs/requests-realtime.md` (есть ли `backend/src/utils/realtime.ts`, маршрут `/staff/events`, `admin/src/services/realtime.ts`). От этого зависит раздел 2. Покажи план и список файлов к изменению — и жди подтверждения.

## 0. Ключевые принципы

1. **Одна инфраструктура на всё.** Шина, поток `/staff/events`, клиент SSE и ведущая вкладка — общие для заявок и заказов. Второго соединения ради заказов не открываем.
2. **Сервер ничего не делает, пока ничего не происходит.** Ни одного опроса по таймеру, пока SSE работает.
3. **Событие — это сигнал.** В событии — только короткая сводка для уведомления, без телефона и адреса. Строку для таблицы админка догружает обычным API.
4. **Каждое изменение заказа проходит через сервис и пишется в историю** (`order-event`). Сейчас смена статуса этого не делает — исправляем.
5. **Публикуем только после фиксации в БД.** Никаких событий из середины DB-транзакции.
6. **Бизнес-логику заказов не меняем:** расчёт цен, оплаты, возвраты, «взять в работу» — как есть.

### 1.1. Проблемы, которые закрывает задача

1. **Смена статуса не попадает в историю.** `PUT /orders/:documentId` меняет статус и `cancelReason` в обход сервиса, `order-event` не пишется — неизвестно, кто и когда отменил или завершил заказ.
2. **Нет единой точки «заказ изменился»**: изменения идут из core `update`, `take`, `recalcOrder` (внутри DB-транзакции), `buildAndCreate`.
3. **Нельзя дать ссылку на заказ** — кнопке «Открыть» в уведомлении некуда вести.

## 3. Бэкенд заказов

### 3.1. События

```ts
type OrderSummary = {
  id: number; documentId: string; code: string;
  status: 'new' | 'accepted' | 'in_progress' | 'done' | 'canceled';
  clientName: string | null;          // без телефона и адреса
  itemsCount: number;                 // сумма qty
  total: number;
  deliveryMethod: 'courier_now' | 'preorder';
  deliverySlotAt: string | null;
  paymentMethod: string;
  source: 'catalog' | 'request' | 'manual';
  createdAt: string;
}

| { scope: 'orders'; type: 'order.created'; orderId: number; summary: OrderSummary; actorId: number | null }
| { scope: 'orders'; type: 'order.updated'; orderId: number; kind: OrderEventKind; status: string; actorId: number | null }
```

`OrderEventKind`: `status_changed`, `taken`, `payment`, `refund`, `txn_canceled`, `updated`.

### 3.2. Единая точка — `orderEvents` в сервисе заказа

В `backend/src/api/order/services/order.ts` добавить:

```ts
async logEvent(orderId: number, kind: string, payload: any, actorId: number | null, note?: string)
  // 1) пишет order-event (как сейчас logOrderEvent в transaction.ts)
  // 2) публикует order.created / order.updated в шину
```

- `logOrderEvent` из `transaction.ts` заменить вызовом `strapi.service('api::order.order').logEvent(...)` — без дублирования кода.
- Для `kind = 'created'` загрузить `OrderSummary` одной выборкой; для остальных — текущий `status`.
- Ошибка публикации не ломает основной запрос: `try/catch` + `strapi.log.warn`.

### 3.3. Где вызывать

| Действие | Где | Событие истории (`kind`) |
|---|---|---|
| Заказ из каталога | `buildAndCreate` (после создания и записи `order-discount`) | `created` (`payload.source`) |
| Ручной заказ / из заявки | то же — `buildAndCreate` | `created` |
| Взять в работу | контроллер `take` после обновления | `taken` (`payload: { from: 'new', to: 'accepted' }`) |
| Смена статуса | **новый** `update` (3.4) | `status_changed` (`from`, `to`, `cancelReason`) |
| Прочие правки через `PUT` | **новый** `update` (3.4) | `updated` (`payload.fields` — какие поля) |
| Оплата / возврат / отмена транзакции | `transaction.ts` — там, где сейчас `logOrderEvent` (уже **после** `strapi.db.transaction`) | `payment` / `refund` / `txn_canceled` — оставить существующие `kind` |

- `createdByEmployee` / `ctx.state.employee` → `actorId`. У заказа из каталога `actorId = null`.
- **Не использовать lifecycles `afterUpdate`** для публикации: `recalcOrder` выполняется внутри DB-транзакции, событие ушло бы до коммита.
- Если заказ создаётся из заявки (`convert`), событие заявки (`request.updated`, `converted`) остаётся как есть — это два разных события.

### 3.4. Переопределить core `update` заказа

В `backend/src/api/order/controllers/order.ts` переопределить `update`:

1. Прочитать текущий заказ (`status`, `cancelReason`) по `documentId`.
2. Вызвать стандартный `super.update(ctx)` — **поведение и ответ API не меняются**.
3. Сравнить: если изменился `status` → `logEvent(id, 'status_changed', { from, to, cancelReason }, employee.id)`; иначе, если изменились другие поля → `logEvent(id, 'updated', { fields }, employee.id)`.

Валидацию переходов статуса и ограничение полей для правки **не добавлять** в этой задаче. Но в отчёте отметь: core `PUT` сейчас позволяет любой роли (включая курьера) менять любые поля заказа, в том числе `total` и `items` — это отдельная задача.

### 3.5. Ссылка на заказ из API

Админка будет догружать строки фильтром по id: `GET /orders?filters[id][$in][0]=…` с тем же `populate`, что в `Orders.vue`. Это стандартный core `find` — новых маршрутов не нужно. Проверь, что `filters` по `id` работает через `is-staff` (sanitize не режет), и отметь в отчёте.

### 3.6. Тесты (`backend/tests/`)

- `buildAndCreate` → `order-event` `created` + публикация `order.created` со сводкой **без телефона и адреса**;
- `PUT` со сменой статуса → `order-event` `status_changed` с `from/to` и автором; без смены статуса → `updated`;
- `take` → `taken`;
- оплата → событие публикуется **после** коммита (подписчик видит уже пересчитанный `paymentStatus`);
- фильтр ролей: курьер получает `order.*` и не получает `request.*`.

## 6. Заказ появляется в таблице — `Orders.vue`

### 6.1. Ссылка на заказ

- Поддержать `/orders?open=<id>`: после загрузки открыть боковую панель этого заказа. Если его нет в загруженном списке — догрузить по id и открыть.
- При открытии панели — обновлять `?open=` в URL (`router.replace`), при закрытии — убирать. Ссылку можно скопировать и отправить коллеге.

### 6.2. Живое обновление списка

- Подписаться на `ordersFeed.onCreated`, `onUpdated`, `onResync` в `onMounted`, отписаться в `onUnmounted`.
- Событие → догрузить заказ(ы) через `Orders.list({ filters: { id: { $in: ids } }, populate: [...как в reload] })` → вставить или заменить в `list` по `id`. Несколько событий за 300 мс — один запрос.
- `onResync` → `reload()` с сохранением открытой панели, фильтров и страницы.
- Фильтры (поиск, статус, «неоплаченные») уже считаются на клиенте в `rows` — новая строка подчиняется им автоматически.

### 6.3. Как выглядит новая строка

- Таблица отсортирована по `createdAt` убыванию — новый заказ встаёт **первой строкой первой страницы**.
- Подсветка: мягкий olive-фон, плавно гаснет за 3–4 с. Метка «Новый» рядом с кодом, пока `id` есть в `unseenIds`.
- Изменённая строка (статус, оплата) — короткая подсветка только ячейки, которая изменилась (статус или оплата), 2 с.

### 6.4. Чтобы не мешать работе

- **Сотрудник не на первой странице** paginator → строка добавляется, страница не переключается. Над таблицей — плашка «↑ N новых заказов · К первой странице».
- **Новый заказ не подходит под фильтр** (например, включён фильтр «Отменён») → над таблицей плашка «N новых заказов не попадают в фильтр · Сбросить фильтры».
- Если идёт ввод в поиске — не сбрасывать поле и фокус.

### 6.5. Открытая боковая панель

- `order.updated` по открытому заказу от **другого** сотрудника → перезагрузить заказ и его транзакции, показать плашку вверху панели: «{Имя} {что сделал}: перевёл в «В процессе» / принял оплату 50 000 сум / отменил: {причина}».
- Если в этот момент открыт диалог оплаты, возврата или отмены — данные не перезагружать до его закрытия, но плашку показать.
- Заказ взял другой сотрудник → кнопка «Взять в работу» исчезает, плашка «Заказ взял {имя}».

### 6.6. История в боковой панели

Раз смена статуса теперь пишется в `order-event`, в панели заказа вывести блок «История» (если его ещё нет): создан, взят, статусы, оплаты, возвраты — кто, когда. Источник — `order.events` (добавить в `populate` при открытии панели, не в общий список).

## 10. Готово, когда

- [ ] Заказ из клиентского каталога появляется у менеджера первой строкой таблицы за 1–2 с без обновления страницы.
- [ ] Появляется уведомление с суммой, количеством позиций и способом доставки; предзаказ показывает дату и время.
- [ ] «Открыть» открывает боковую панель заказа; ссылка `/orders?open=<id>` работает и из адресной строки.
- [ ] «Взять в работу» из уведомления берёт заказ; если его уже взяли — уведомление говорит, кто.
