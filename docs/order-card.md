# SoupPack — Карточка заказа: процесс по этапам

Техническое задание для Claude Code. Переделываем боковую панель заказа в `admin/src/pages/orders/Orders.vue`:

1. **Весь процесс заказа виден сразу** — вертикальный список этапов с описанием: какие пройдены (кто и когда), на каком заказ сейчас и что сделать, какие впереди.
2. **Панель шире и красивее**, с понятными блоками.
3. **Прокручивается только панель**, страница под ней — нет.
4. **Открытый заказ выделен в таблице**, остальные строки полупрозрачные.

> Перед началом прочитай этот файл целиком, затем `docs/orders-realtime.md` (живое обновление заказов — уже сделано, не сломать) и текущий код из раздела 1. Если код расходится с описанием — ориентируйся на код и отметь расхождение в итоговом отчёте.
>
> Сначала покажи план и список файлов к изменению — и жди подтверждения.

---

## 0. Ключевые принципы

1. **Этапы — одна конфигурация.** Названия, описания, подсказки, действия этапов — в одном файле (`admin/src/utils/orderFlow.ts`). Панель, таблица и уведомления берут их оттуда.
2. **Кто и когда — из истории заказа** (`order-event`), а не из догадок по полям.
3. **Главное действие — всегда в текущем этапе.** Сотрудник видит, где заказ сейчас, и одну понятную кнопку «что дальше».
4. **Живое обновление сохраняется**: события `order.updated` из `ordersFeed` обновляют этапы в открытой панели.
5. **Расчёт цен, оплаты, возвраты не трогаем.**

### 1.1. Проблема в процессе: шаг «Подтвердить» никогда не показывается

`take` сразу ставит статус `accepted`, поэтому условие кнопки «Подтвердить» (`есть сотрудник && status === 'new'`) не выполняется никогда. При этом подсказка в коде говорит: «Подтвердить = сотрудник позвонил клиенту, перечислил заказ и получил устное подтверждение». То есть задуман отдельный этап звонка клиенту, но он склеен со «взять в работу».

**Решение:** разделить — `take` только закрепляет сотрудника, статус остаётся `new`; подтверждение после звонка — отдельный шаг `new → accepted`. См. 2.2 и 3.1.

## 2. Процесс заказа

### 2.1. Этапы

| # | Этап | Когда пройден | Описание для сотрудника | Действие на этом этапе |
|---|---|---|---|---|
| 1 | **Поступил** | всегда (создание заказа) | Заказ оформлен {из каталога / из заявки RQ-… / вручную}. | — (этап пройден сразу) |
| 2 | **Взят в работу** | есть `employee` | Сотрудник отвечает за заказ до конца. Пока заказ ничей — его может взять любой. | **«Взять в работу»** |
| 3 | **Подтверждён клиентом** | `status` ≥ `accepted` | Позвоните клиенту: проверьте состав, адрес и время доставки, способ оплаты. Подтверждайте после устного согласия клиента. | **«Клиент подтвердил»** (диалог 2.3) |
| 4 | **Готовим и доставляем** | `status` ≥ `in_progress` | Заказ собирается и передаётся в доставку. {Для предзаказа: «Доставка к 05.11, 12:00».} | **«Передать в работу»** (accepted → in_progress) |
| 5 | **Завершён** | `status = done` | Заказ доставлен клиенту. | **«Завершить»** (in_progress → done) |

- Отмена — не этап, а выход из процесса на любом шаге 1–4 (см. 2.4).
- Статусы в БД **не меняются** (`new / accepted / in_progress / done / canceled`). Этап 2 вычисляется по наличию `employee`.
- Названия кнопок и статусов в таблице и фильтрах привести к этим этапам (раздел 5): статус `accepted` в интерфейсе — «Подтверждён», `in_progress` — «Готовим и доставляем», `done` — «Завершён», `new` без сотрудника — «Новый», `new` с сотрудником — «Взят».

### 2.2. Кто и когда — из истории

| Этап | Событие `order-event` | Если события нет (старые заказы) |
|---|---|---|
| Поступил | заказ `createdAt`, `source` | — |
| Взят в работу | `taken` (актор) | только имя из `employee`, без времени |
| Подтверждён | `status_changed` с `to = accepted`; для старых заказов — `taken` с `to = accepted` | «время неизвестно» |
| Готовим и доставляем | `status_changed` с `to = in_progress` | «время неизвестно» |
| Завершён | `status_changed` с `to = done` | «время неизвестно» |
| Отменён | `status_changed` с `to = canceled` (+ `cancelReason`) | причина из `order.cancelReason` |

Функция `buildOrderStages(order, events, now)` в `utils/orderFlow.ts` возвращает массив этапов:

```ts
type Stage = {
  key: 'created' | 'taken' | 'confirmed' | 'in_progress' | 'done'
  title: string
  description: string            // с подставленными данными заказа
  state: 'done' | 'current' | 'upcoming' | 'skipped'   // skipped — после отмены
  at: string | null              // когда пройден
  actor: { id: number; fullName: string } | null
  durationMin: number | null     // сколько длился этап / сколько уже идёт текущий
  action: StageAction | null     // только у текущего
}
```

Покрыть unit-тестами (`admin` — vitest, если подключён; если нет — подключить только для этого файла и отметить в отчёте).

### 2.3. Диалог «Клиент подтвердил»

Небольшой `Dialog` вместо мгновенной смены статуса — это напоминание, что проверить при звонке:

- заголовок «Подтверждение заказа {код}»;
- телефон клиента крупно, ссылка `tel:` и кнопка «Скопировать»;
- чек-лист (галочки только в интерфейсе, в БД не хранятся): «Состав и количество», «Адрес» (адрес текстом), «Время доставки» (сейчас / дата предзаказа), «Способ оплаты» (метод);
- необязательный комментарий — пишется в событие `status_changed` как `note` (передать в `PUT` полем, которое сервер положит в `note` события — см. 3.2);
- кнопки «Назад» и «Клиент подтвердил». Кнопка активна, когда отмечены все пункты.

### 2.4. Отмена

- Кнопка «Отменить заказ» — на этапах 1–4, **вторичная** (текстовая, tomato), в шапке панели, а не рядом с главной кнопкой этапа, чтобы не нажать случайно.
- Диалог причины — существующий.
- Отменённый заказ: пройденные этапы — как были (зелёные), этап, на котором отменили, — красный с крестиком: «Отменён {кто}, {когда}. Причина: …»; последующие — `skipped` (серые, зачёркнутые названия).
- Если по отменённому заказу есть оплата — под этапом предупреждение «Нужен возврат: N сум» с кнопкой «Возврат» (только `manager`, как сейчас).

### 2.5. Оплата и процесс

Оплата — отдельный блок (не этап), но связана с процессом:
- на этапе 4 при нажатии «Завершить», если заказ не оплачен полностью, — подтверждение «Заказ не оплачен: остаток N сум. Завершить без оплаты?» с кнопками «Принять оплату» (открывает существующий диалог) и «Завершить всё равно». **Не блокировать** — только предупредить.

## 3. Бэкенд

### 3.1. `take` — только закрепление сотрудника

В `backend/src/api/order/controllers/order.ts` → `take`:
- убрать шаг «Статус new → accepted»;
- событие `taken` — `payload: { employeeId }` (без `from/to`).

Последствия, которые нужно проверить и поправить:
- `admin/src/stores/ordersFeed.ts` и `OrderToast.vue` — если «заказ взят» определяется по `status === 'accepted'`, перейти на `kind === 'taken'` / наличие сотрудника;
- `RequestToast`/`ordersFeed` — непросмотренный заказ убирается из `unseenIds` при `taken`;
- `Dashboard.vue` и `/staff/dashboard` — проверить, что подсчёты по статусам не ломаются (заказ в `new` с сотрудником);
- клиент (`client/src/pages/OrderPage.vue`, `AccountPage.vue`) — клиент теперь видит «Новый», пока сотрудник не подтвердил заказ звонком, и «Принят» — после. Это ожидаемое поведение, менять клиент не нужно; отметь в отчёте.

### 3.2. Комментарий к смене статуса

В переопределённом `update` заказа (сделан в `orders-realtime.md`) принять необязательное поле `statusNote` (не поле схемы — вырезать из `data` до `super.update`) и записать его в `note` события `status_changed`.

### 3.3. История для панели

При открытии панели заказ загружается с `events` и их `actor` (`populate: { events: { populate: ['actor'] } }`) — проверь, что так уже сделано; если нет — добавить в загрузку одного заказа, **не** в общий список.

### 3.4. Тесты

- `take` не меняет статус, пишет `taken`; повторный `take` → `ALREADY_TAKEN`;
- `PUT` со `statusNote` → `note` в событии, `statusNote` не попадает в заказ.

## 4. Боковая панель заказа

### 4.1. Компонент и поведение

- Вынести панель из `Orders.vue` в `admin/src/pages/orders/components/OrderPanel.vue` (props: `order`, `events`, `transactions`; emits действий). `Orders.vue` и так 900+ строк.

- **Не модальная:** без тёмной подложки на весь экран (`:modal="false"`), чтобы таблица оставалась видимой и кликабельной (раздел 6). Закрытие: крестик, `Esc`, клик по свободной области страницы вне таблицы и панели.
- **Прокрутка:**
  - пока панель открыта, страница не прокручивается: на `<html>` класс `overflow-hidden`, снимается при закрытии и при уходе со страницы (`onUnmounted`). Добавить `scrollbar-gutter: stable` на `html` в `assets/style.css`, чтобы при скрытии полосы прокрутки страница не сдвигалась;

### 4.2. Шапка (закреплена)

### 4.3. Блок «Процесс» — первый в теле панели

Вертикальный степпер — главное в панели.

```
 ✓  Поступил                                   14:32 · из каталога
 │
 ✓  Взят в работу                     Азиз · 14:35 · через 3 мин
 │
 ◉  Подтверждён клиентом                              идёт 9 мин
 │  Позвоните клиенту: проверьте состав, адрес и время доставки,

```

- **Пройденный** этап: зелёный (olive) круг с галочкой, сплошная линия вниз; название, справа — кто, когда, сколько занял («через 3 мин»). Описание скрыто, раскрывается по клику.
- **Текущий**: круг с цветным кольцом и мягкой пульсацией (без анимации при `prefers-reduced-motion`); фон этапа выделен (светлая подложка, скругление); описание полностью; главная кнопка этапа (primary) и полезные быстрые действия (для этапа 3 — телефон с `tel:`). Справа — «идёт N мин» (обновлять раз в минуту).
- **Будущие**: серый пустой круг, пунктирная линия; название и описание одной строкой серым.
- **Отменённый** — см. 2.4.
- Кнопка «Взять в работу» на этапе 2 — при `ALREADY_TAKEN` как сейчас: предупреждение и обновление.
- После действия: кнопка в состоянии загрузки, затем этап плавно становится пройденным, следующий — текущим (переход 200–300 мс).

### 4.4. Остальные блоки (карточки с заголовком и иконкой)

Порядок под «Процессом»:

1. **Клиент** — аватар с инициалами, имя, телефон (`tel:` + «скопировать»), ссылка на клиента в админке, если есть страница клиента; «N-й заказ клиента», если легко посчитать — иначе не делать.
2. **Доставка** — способ: «Курьером сейчас» / «Предзаказ на 05.11, 12:00» (для предзаказа — «через 2 ч 10 мин» или «просрочен на …» tomato); адрес текстом + «скопировать» + «Открыть на карте» (существующая ссылка); комментарий клиента, если есть.
3. **Состав заказа** — существующий чек (товары, наборы, скидки, итоги) без изменения логики; визуально: строки с разделителями, суммы выровнены по правому краю, итог крупно.
4. **Оплата** — существующий блок: сумма / оплачено / остаток, кнопки «Принять оплату» и «Возврат», история транзакций.
5. **История** — лента событий с понятными подписями и иконками вместо сырых кодов:

| `kind` | Подпись |
|---|---|
| `created` | Заказ создан {из каталога / из заявки RQ-… / вручную} |
| `taken` | Взят в работу |
| `status_changed` | {Подтверждён клиентом / Передан в работу / Завершён / Отменён: причина} + `note`, если есть |
| `payment` | Оплата +N сум · метод |
| `refund` | Возврат −N сум · метод |
| `txn_canceled` | Сторно транзакции {код} |
| `updated` | Изменены поля: {человеческие названия полей} |

Новые сверху, автор и время справа. Свернуть до 5 последних с кнопкой «Показать всё».

## 6. Выделение открытого заказа в таблице

- Пока панель открыта, у всех строк таблицы, кроме открытой, — `opacity: 0.4` с плавным переходом 200 мс.
- Открытая строка: полная непрозрачность, фон `cream-50`, слева акцентная полоса 3px цвета текущего этапа.
- Наведение на полупрозрачную строку → `opacity: 0.8`; клик — переключает панель на этот заказ (без закрытия и повторного открытия, `?open=` обновляется).
- Шапка таблицы, фильтры и сводка — без затемнения.
- Подсветка новых заказов из реального времени (`order-flash`) работает и на полупрозрачных строках.
- Paginator: если открыт заказ не с текущей страницы (пришли по ссылке `?open=`), — переключить таблицу на страницу, где он есть; если его нет в загруженном списке — выделения нет, панель всё равно открыта.
- Клавиатура (если просто сделать): `↑` / `↓` при открытой панели — предыдущий / следующий заказ в текущем отфильтрованном списке.
- Важно: панель не должна перекрывать открытую строку. При ширине панели 880px и узком окне открытая строка может уйти под панель — в этом случае прокрутить таблицу по горизонтали к колонкам «Код» и «Клиент» нельзя, поэтому колонки «Код» и «Клиент» должны быть слева (как сейчас), а таблица — занимать всё место слева от панели.

## 9. Готово, когда

- [ ] В панели заказа сразу видны все 5 этапов; пройденные — с галочкой, кем и когда; текущий — с описанием, временем на этапе и одной главной кнопкой; будущие — серые.
- [ ] «Взять в работу» закрепляет сотрудника, статус остаётся «Новый»; следующий этап — «Подтверждён клиентом» с кнопкой «Клиент подтвердил» и диалогом-чек-листом.
- [ ] Полный проход Поступил → Взят → Подтверждён → Готовим и доставляем → Завершён работает, каждый шаг появляется в истории с автором и временем.
- [ ] Отмена на любом этапе показывает, на каком этапе и почему отменили; дальнейшие этапы — серые зачёркнутые.
- [ ] «Завершить» неоплаченный заказ — предупреждение с кнопкой «Принять оплату».
- [ ] История показывает понятные подписи, а не коды (`taken`, `status_changed`).
- [ ] Панель шире (880px на большом экране), шапка закреплена, прокручивается только содержимое панели; страница под ней не прокручивается и не сдвигается.
- [ ] При открытой панели остальные строки таблицы полупрозрачные, открытая выделена; клик по другой строке переключает заказ.
- [ ] Ссылка `/orders?open=<id>` открывает панель и выделяет строку на нужной странице таблицы.
- [ ] Изменение заказа другим сотрудником обновляет этапы в открытой панели в реальном времени.
- [ ] Колонка «Этап» в таблице с мини-прогрессом; фильтры «Новый» и «Взят» разделены.
- [ ] Тесты проходят.
- [ ] Итоговый отчёт: что сделано, расхождения с ТЗ, влияние изменения `take` на клиентское приложение и статистику.
